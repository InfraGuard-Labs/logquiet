# Benchmarks

All numbers below are real measurements from this repository's own
benchmark tooling, run on the development machine (Windows 11, Intel Core
i5-8265U @ 1.60GHz, 4 cores/8 threads), not estimates or aspirational
targets. Reproduce them yourself with the commands shown in each section -
nothing here depends on hardware or data you cannot generate locally.

Absolute throughput numbers are machine- and Go-runtime-dependent and will
differ on your hardware. What should hold everywhere: memory stays
bounded regardless of input size, and known-important events are never
lost regardless of suppression ratio.

## How to reproduce

```bash
# Correctness + retention (fast, seconds)
go run ./tools/fixturegen correctness
go run ./benchmarks/correctness --json benchmarks/results/correctness-latest.json

# Raw throughput corpora (100K/1M/10M lines; 10M is a few hundred MB)
go run ./tools/fixturegen perf 100000  mixed benchmarks/data/mixed-100k.log
go run ./tools/fixturegen perf 1000000 mixed benchmarks/data/mixed-1m.log
go run ./tools/fixturegen perf 1000000 repetitive benchmarks/data/repetitive-1m.log
go run ./tools/fixturegen perf 1000000 diverse    benchmarks/data/diverse-1m.log
go run ./tools/fixturegen perf 10000000 mixed benchmarks/data/mixed-10m.log

logquiet --plain --stats benchmarks/data/mixed-100k.log > /dev/null
# ... etc for each corpus; --stats prints the summary to stderr
```

Micro-benchmarks for individual pipeline stages:

```bash
go test ./internal/normalize/ -bench=. -run=^$
go test ./internal/pipeline/  -bench=. -run=^$
```

## Correctness benchmark: known-important-event retention

The most important safety metric for a tool whose entire purpose is
hiding most of its input is **not compression ratio** - it is whether the
handful of lines that actually mattered survived. `benchmarks/correctness`
runs the real pipeline (in-process, same code as the shipped binary)
against ten realistic synthetic fixtures (`fixtures/synthetic/`, each with
a manifest of substrings that must survive to the output; see
[the fixtures README](../fixtures/synthetic/README.md)) and fails the
build if any known-important event is missing from the output.

Current results (also machine-checked in CI):

| Scenario | Lines | Displayed | Suppression | Patterns | Known-important retained |
|---|---:|---:|---:|---:|:---:|
| Kubernetes pod restart loop | 321 | 9 | 97.2% | 9 | 2/2 |
| Database connection exhaustion | 337 | 6 | 98.2% | 6 | 2/2 |
| HTTP service failure | 521 | 5 | 99.0% | 5 | 1/1 |
| Java/Spring exception | 237 | 2 | 99.1% | 2 | 2/2 |
| Python traceback | 196 | 2 | 99.0% | 2 | 1/1 |
| Node.js exception | 194 | 2 | 99.0% | 2 | 1/1 |
| Go panic | 138 | 2 | 98.5% | 2 | 1/1 |
| CI deployment failure | 105 | 16 | 84.8% | 16 | 2/2 |
| Auth failure burst + lockout | 551 | 3 | 99.5% | 3 | 1/1 |
| Healthy noisy service -> fatal OOM | 2001 | 5 | 99.8% | 5 | 1/1 |

**100% retention across all ten scenarios**, alongside 85-99.8%
suppression. This table is regenerated by `go run ./benchmarks/correctness`
and should be treated with suspicion if it is ever edited by hand instead
of by running that command.

### A regression this suite actually caught during development

An earlier version of the renderer only collapsed *strictly consecutive*
repeats of the same pattern. Against the Kubernetes restart-loop fixture -
which cycles through eight distinct log lines per restart, so the same
pattern never repeats back-to-back - this produced **0% suppression**
(321 lines in, 321 displayed), silently failing the entire point of the
tool on a very ordinary log shape. The fix (accumulate-and-periodically-
flush per pattern, independent of interleaving - see
[TECHNICAL_METHOD.md](TECHNICAL_METHOD.md) section 5) brought that
scenario to 97.2% suppression with retention unchanged. This is reported
here rather than omitted because a benchmark suite that only ever shows
success after the fact is not evidence of anything; the point of running
it continuously during development was to catch exactly this kind of
regression before release, and it did.

## Throughput

| Corpus | Lines | Profile | Elapsed | Lines/sec | MB/sec | Approx. memory |
|---|---:|---|---:|---:|---:|---:|
| `mixed-100k.log` | 100,002 | 90% repetitive / 10% diverse | 6.32s | 15,818 | 1.19 | 2.4 MB |
| `mixed-1m.log` | 1,000,020 | 90% repetitive / 10% diverse | 49.70s | 20,121 | 1.51 | 2.1 MB |
| `repetitive-1m.log` | 1,000,020 | fully repetitive (per service) | 41.98s | 23,819 | 1.77 | 2.3 MB |
| `diverse-1m.log` | 1,000,020 | fully unique (adversarial - see below) | 96.46s | 10,367 | 1.02 | 12.9 MB |
| `mixed-10m.log` | 10,000,200 | 90% repetitive / 10% diverse | 495.07s | 20,200 | 1.52 | 1.8 MB |

`--stats` reports `approx memory` from Go's `runtime.MemStats.Alloc` at
the end of the run, not a sampled peak - real peak RSS is somewhat higher
due to allocator overhead, but the trend (memory does not grow with input
size once patterns saturate) is the property that matters, and it holds:
**1.8-2.4 MB for the realistic (mixed/repetitive) corpora from 100K to
10M lines**, because the pattern store is bounded regardless of stream
length - the 10M run used *less* measured memory than the 100K run at the
moment `--stats` sampled it, which is expected GC-timing noise around an
already-small, flat baseline, not a trend. Run-to-run throughput variance
of 10-20% is normal on a shared development laptop (the `mixed-100k`
figure above, for instance, ran slower than the larger `mixed-1m` corpus
in the same batch, almost certainly background system load rather than a
real "smaller is slower" effect) and is reported as measured, not smoothed
over.

### The `diverse-1m.log` result is a deliberately adversarial case, explained

That corpus gives every one of its 1,000,020 lines a unique alphabetic
marker specifically so structural normalization *cannot* collapse it -
every single line is a genuinely novel pattern. This is close to a
worst case for this tool's design (constant pattern creation and LRU
eviction, no suppression to amortize the per-line cost against), and it
is reported here rather than cherry-picked out:

- **0% suppression, 1,000,020/1,000,020 displayed** - correct: there was
  nothing to suppress.
- **`structural patterns: 10000 (evicted 990020)`** - the pattern store's
  bounded-memory guarantee (default `--max-patterns 10000`) held exactly
  at the configured limit under one million-line sustained pressure,
  evicting the other 990,020 as designed rather than growing without
  bound. Memory stayed at 12.9 MB (higher than the other runs, because a
  full LRU of 10,000 live patterns is being maintained, but still small
  and still bounded).
- Throughput drops to 10,367 lines/sec under this specific adversarial
  shape, versus 15,800-23,800 lines/sec for the mixed/repetitive corpora
  that resemble real infrastructure logs (which are rarely "every single
  line is globally unique forever"). This is reported as the honest
  worst-case number, not hidden.

### What limits throughput today

Profiling (`internal/normalize.BenchmarkTemplate`,
`internal/pipeline.BenchmarkProcessLineRepetitive/Diverse`) shows
structural normalization dominating per-line cost even after the
optimization described in [TECHNICAL_METHOD.md](TECHNICAL_METHOD.md)
section 2 (a roughly 2.8x improvement over the first working version, from
~130us/line to ~46us/line on a representative line). At current
throughput, LogQuiet processes tens of thousands of lines per second with
enormous headroom over realistic live `kubectl logs -f`/`tail -F` rates
(real services rarely sustain more than a few thousand lines/sec, even
when noisy), and processes a 10-million-line historical file end-to-end
in about 8 minutes on a mid-range laptop (495s measured above). Further throughput work
(hand-rolling more of the remaining regex-based classes, or adding a cheap
"no digit/hex character present" pre-filter to skip normalization entirely
on many real log lines) is a reasonable direction for a future version and
is not needed for the tool to be useful today.

## Scaling with pattern cardinality

`internal/pipeline.TestBoundedMemoryUnderHighCardinality` and the
`diverse-1m.log` run above are the two data points on this axis: pattern
tracking is a hash map bounded by `--max-patterns` (default 10,000) with
LRU eviction, so memory is flat with respect to *stream length* and scales
only with the *bound itself*, not with how many total distinct patterns
have ever been seen. Raising `--max-patterns` trades memory for the
ability to keep more simultaneous distinct patterns "warm" before their
history is forgotten (see [ARCHITECTURE.md](ARCHITECTURE.md) "Known
limitations" for what eviction means for a pattern that reappears later).
